## 交接：召回优化（下一个 session 从这里开始）

### 现状：四路召回，并集，按"命中路径数"排序

`qa.py::recall()`，取前 `QA_MAX_SOURCES=40` 条：

| 路由 | 怎么找 | 局限 |
| --- | --- | --- |
| **entity** | 从问题里抽出的实体 → `pkb_index.search_entities` → 该实体的全部消息 | 依赖实体抽取质量；一个问题里抽不到实体就整路失效 |
| **text** | 每个检索词 `LIKE` 正文 + metadata（含附件 OCR，两种转义形态都试） | **字面匹配**：换个说法就搜不到；`LIKE` 无索引 |
| **gist** | 检索词匹配 `pkb.db` 里的一句话摘要 | 摘要本身是模型写的，可能漏掉关键词 |
| **日历** | 问题含时间词（接下来/什么时候/到期…）时，把 `event_date` 在未来的消息全加进来 | 关键词表是硬编码的 |

排序：按命中**路径条数**降序，同分按 id。**没有相关性打分**。

### 已经量出来的缺口（都还没修）

1. **泛词污染**。真实案例（"我明天去奥斯丁的飞机几号航站楼"）：
   最具体的两个词 `座位号` 命中 **0** 条、`航站楼` 4 条；最没区分度的
   `明天` 11 条、`seat` **12 条**、`机场` 9 条。最后**采用 40 条里只有 3 条提到 Austin**，
   真证据被埋了。→ 需要**按词频降权或剔除泛词**（一个词命中比例过高就是噪声）。
2. **没有相关性打分**。命中路径数是很粗的代理：一条被"泛词"命中的消息和一条被
   实体命中的消息权重一样。
3. **`LIMIT 60` 是任意的**，每路独立截断，可能把关键消息截在后面。
4. **召回上限 40 是硬编码的**，和"问题需要多少条"无关。
5. **同一事件的重复没折叠**（短信 + 同一条短信的推送），时间线里成对出现，占配额。
6. **附件级别没有身份标注**。实锤：一条消息里装着**两本护照**（旧的 2010–2020、
   新的 2019–2029），而两个附件叫 `passport.pdf` 和 `[Untitled].pdf`——
   **文件名不说明哪本是哪本**，模型只能靠号码猜，于是同一份文本它有时说"有有效期"、
   有时说"没写"。→ 需要给附件一个"这是什么"的标注（OCR 首行 / 识别出的证件类型）。
7. **`rewritten` 只用于生成检索词，没参与检索**。改写后的完整问句被丢弃了。
8. **没有评估集**。研究结论原话：*"唯一可靠的是拿自己 200 条真实查询自测"*——
   现在只有 14 条问答记录、其中 5 条 👎。**没有这套东西，任何"优化"都无法证明有效。**

### 该先做的事（我的建议，供讨论）

**第一步不是改召回，是把评估集建起来**：把那 5 条 👎 展开成一组（问题 → 期望命中的消息 id），
再加若干条已知答案的问题（MOT 到期日、租车取还车、简单心理付款与退款、护照两本的号码与有效期、
接下来有什么安排）。有了它，"召回改了到底有没有变好"才是可测的，否则每一次调整都只是感觉。
`qa_turns` 里已经存了每次的 `sources`，可以直接拿来当"基线召回"做对比。

然后才是：按词频降权 / 相关性打分 / 折叠重复 / 附件身份标注。

### 明确的"不做"（避免重新讨论）

* **不换服务器上的 OCR 组件**：RapidOCR 实测 9–14 秒/页、**峰值内存 478MB**，
  而那台机 960MB 且 OCR 跑在 gunicorn 进程里——要换必须先把它挪出 Web 进程，
  多半还要升内存。已量过，写在 `docs/ocr.md`。（我建的那套测试环境已删。）
* **不解析 MRZ**：用户否掉了。而且实测证明没必要——把图读对之后，
  **印上去的有效期**（`16 7月/JUL 2029`）就能读出来。
* **外部查询（agentic）**：记为后期。前提是回答里必须**分开标注**"库里有据"和"网上查的"。

## 踩过的坑（重犯一次就白记了）

1. **`db.create_all()` 不给已有表加列。** 踩了两次（`messages.natural_key`、`qa_turns.cost`），
   现在 `migrate.py` 有一份"后加列"的显式清单 + 幂等 ALTER 循环。
2. **实体 id 不能用自增整数。** 表是每次重建时从零建的、插入顺序取决于并发批次谁先跑完，
   于是每重建一次所有 id 全重排（张丽捷 71→66，而 71 变成另一个人），
   打开着的页面、书签、问答历史全指错人。现在是名字的 sha1 前 16 位。
3. **JSON 列里的非 ASCII 是转义的。** 拿 `%中文%` 去 `LIKE` 永远 0 条；
   要拿 `json.dumps(term)` 产出的转义形态去比。
4. **SQLAlchemy 的 JSON 列必须 deepcopy 后整体赋值。** 浅拷贝里改内层 dict，
   新旧值比较相等，**UPDATE 根本不发出**（`reset_status` 静默失效就是这么来的）。
5. **OCR 会把空格插进机读区**，任何"前面不能是字母数字"的边界断言都会失效；
   比对前先把空白全去掉。（这条是写 MRZ 解析器时踩的，代码已删，教训留着。）
6. **测量本身会错。** 第一次跑 OCR 参数矩阵时 grep 没去空格，报告了假的"机读区=0"；
   第一次写"计数一致"的测试是同义反复（测试里自己按正确顺序调两步再断言），
   靠**反向验证**（把代码改回错的，测试必须失败）才发现。
7. **`android_client` 的 `MAX_RETRY_COUNT=5` × 每个通知触发一次全量同步 = 洪水。**
   15,745 条重复就是这么来的（详见 `docs/idempotency.md`）。
