# ANKS（AI-native Knowledge System）— Obsidian 的个人知识微内核

> **来源**：用户转述的 14 篇笔记摘要（2026-09-21）。
> **说明**：本文忠实记录转述内容；**我没有读过 ANKS 的原始材料**，下面"要点"部分不代表我核验过的事实，

## 1. 原文要点（按转述记录）

### 1.1 核心理念：告别手动整理

传统知识管理会陷入"为笔记维护复杂文件夹结构"的困境：笔记状态一变（草稿→发布）就要手动搬文件。
ANKS 的主张是**文件夹结构不需要人工维护**，原则是：

> **路径是元数据的投影。**

你只改元数据（状态、类型），系统按预设规则把文件"放"到正确的逻辑路径上，无需拖拽。

### 1.2 三个平面（顶层只有三个目录）

| 平面 | 是什么 |
|---|---|
| **Topics** | 日常工作区。每个 Topic 对应一个希望持续研究的领域 |
| **Core** | 跨 Topic 可复用的、最通用的知识。**从 Topic 升入 Core 需要审批** |
| **Sidecar** | 系统运行所需的工具、索引、日志。日常基本不需要触碰 |

### 1.3 四个坐标（知识靠这四个坐标定位）

| 坐标 | 含义 |
|---|---|
| **Raw** | **证据层**：未经处理的原始资料（剪藏的网页、PDF 等） |
| **Source** | **参考层**：由 AI Agent 把 Raw 规范化整理而成——作者、出处、关键主张 |
| **Knowledge** | **综合层**：消化多个来源后形成的**自己的理解**，持续演化的"活文档" |
| **Output** | **表达层**：面向特定场景产出的内容（文章、报告等） |

### 1.4 分工模式：人 / Agent / 程序

| 角色 | 负责 | 关键约束 |
|---|---|---|
| **人** | 设定目标、做判断、**审批**、确认事实；决定什么知识值得长期保留 | — |
| **Agent（LLM）** | 语义理解：判断一段文字是想法/问题/知识，给出分类建议与置信度 | **不直接操作文件** |
| **程序（Router/Script）** | 确定性操作：读 Agent 产出的元数据，按配置文件（TOML）里的规则移动/重命名文件 | 规则是确定性的 |

### 1.5 适用性与注意事项（作者自陈）

- **学习成本**：要理解元数据的含义，并适应"改状态而不是搬文件"的操作方式。
- **系统反馈**：有用户反映**系统偏复杂、上手有难度**；作者提到未来可能做图形界面降低门槛。
- **关键认知**：**这是一个系统架构思想，不是即装即用的插件。**

## 2. 与我们的对照

| ANKS | 我们（见 `info_agent/docs/pkb-model.md`） |
|---|---|
| Raw = 证据层，未处理 | `raw/` 不可变、永久保留、唯一真相来源 —— **同一件事** |
| Source = AI 规范化的参考（作者/出处/关键主张） | `观察`(obs) + 来源指针；规范化由代码做 —— **同一个位置** |
| Knowledge = 你自己的综合，"活文档" | `实体 / claim` 层 + 渲染出来的页面 —— **同一个位置** |
| **Output = 面向场景的产出** | **我们没有对应物**（见 §4） |
| Topics / Core / Sidecar | 我们是 `wiki/{people,orgs,events,topics}` + `index.md`/`log.md`，**没有"晋升"机制，也没有把 Sidecar 显式当成一层** |
| **路径是元数据的投影** | 我们已经是"页面由 compile 生成"，但**没有把"人永不手动移动文件"当成纪律写下来** |
| Agent 给**建议 + 置信度**，**不直接改文件** | **完全相同**：LLM 只提议关系、给置信度；代码裁决不变量 |
| 升入 Core 需**审批** | 我们的"低置信 → 待确认队列"是同一个原语，但只用在实体合并上，没用在知识晋升上 |
| 靠**目录**组织（一个笔记一个路径） | 靠**图**组织（节点 + 边，多对多）—— **最实质的差别**，见 §5 |

## 3. 它独立验证了我们的一条原则

ANKS 是**第四个**独立到达同一个结论的来源：

> **确定性结构由程序掌管，LLM 只碰内容层，且只给建议、不直接改数据。**

这和我们已经记下的收敛结论 #1 完全一致（Karpathy 说 schema 是关键配置文件；Obsidian 生态说"绝不让 LLM 决定文件放哪、要不要新建笔记"；记忆系统调研说"写时抽取结构化事实反而掉分"）。
四个来源、四种语境、同一个答案 —— 这条可以当作定论了。

## 4. 它给了我们几件新东西（建议采纳）

### 4.1 「路径是元数据的投影」——这条直接解决我们一个悬着的问题

我们一直没答：**两个实体合并之后，文件怎么办？**
（真实案例：`people/zhang-li.md` 与 `people/zhang-lijie.md`，看着是同一个人但无法证明。）

ANKS 这条原则给出的答案是：

> **身份用 UUID，路径由 `(kind, 名字)` 投影出来，合并只改元数据，文件由程序自动归位。**
> 人**永远不手动移动或重命名**文件。

于是"合并"退化成改一条边（`same_as`），路径自动重算 —— 这正是我们想要的"可撤销"。
**建议采纳为纪律。**

### 4.2 给"产出"一个家（Output 层）

我们的模型里**没有位置放"我产出的东西"**：一份分析、一张对比表、一次讨论的结论。
Karpathy 那条"**好答案要回填成新页面**，别让它消失在聊天记录里"说的也是这个，但我们没给它建模。

**建议**：`实体.kind` 里加一类 `output`，或直接按目录约定给它一个位置。成本极低。

### 4.3 「晋升需要审批」这个原语用两次

ANKS 用它管"Topic → Core"；我们用它管"实体合并"。
同一个东西：**低置信 / 高影响的操作 → 进人工队列**。
**建议**：把它当**一个通用 gate 机制**实现一次，两处复用，而不是各写一套。

### 4.4 把 Sidecar 显式当成一层

工具、索引、日志、缓存单独一层，并明确"**日常不用碰、可重建**"。
我们已经有 `index.md`/`log.md` 和"视图可重建"的说法，但没有把它写成一条边界。
**建议**：写下来，防止以后有人往里面手写内容。

## 5. 它没有覆盖我们的哪些问题（都有真实数据支撑）

| 我们面对的问题 | ANKS 为什么不需要面对 |
|---|---|
| **判重（新的/重复的/冲突的/版本）** | ANKS 的输入是**人主动剪藏的网页和 PDF**——每一篇都是人有意放进去的，天然不重复。我们的输入是**自动流入的通知/短信/邮件**。 |
| **节点身份（实体消歧 / 别名 / 合并）** | 对"人写的笔记"来说，**标题就是身份**。我们这边这是最难的环节：`张丽吗喽`(微信) vs `张丽捷`(+447907011046，2018 年护照扫描件证实真名)——**没有任何证据能证明是同一人**，只能进待确认队列。ANKS 的四坐标里没有这一层。 |
| **时效 / 有效期 / 取代链** | 它的四个坐标是**知识的成熟度**（Raw→Source→Knowledge→Output），不是**事实的时效**。我们需要的"租车 10-01→10-06 有效""MOT 10-16 到期""09-22 19:00 有一场预约"在它的模型里没有位置。 |
| **一条信息同时属于多个事物** | **目录树只能给单值归属**：一篇笔记只能在一个路径下。而我们的一条观察可以同时关于一次行程、一个人、一个机构。**用目录表达多对多是做不到的——这正是我们选择"图（节点+边）"而不是"目录树"的原因。** |

> 一句话：**ANKS 解决的是"知识怎么放"，我们还要额外解决"信息是什么、和什么有关"。**
> 它的四个坐标覆盖了我们问题的一半（Raw / Source / Knowledge 三层语义几乎一一对应），
> 另一半（判重、身份、时效、多对多）是我们自己在填。

---

## 6. 结论

**记录在案，采纳 3 条纪律，不采纳它的组织结构。**

**采纳**：
1. 路径是元数据的投影；身份用 UUID；**人永不手动移动文件**
2. 给"产出"一个位置（Output 的概念）
3. 把"人工审批 gate"实现成**一个**通用原语，实体合并与知识晋共复用

**不采纳（当前规模）**：
- Topics / Core 的三平面划分与"升入 Core"的流程 —— 我们的研究结论是 <1000 条语料下知识图谱/复杂组织**基本无收益**（带/不带相关性 0.83 vs 0.81），先不做
- 用 TOML 规则文件驱动路由 —— 我们的路径生成已经在代码里，再引一层配置语言只是多一个要维护的东西

**最有价值的一点**：它**独立验证了"LLM 只提建议、程序做决定"**，并且用一条很干净的原则（路径是元数据的投影）解决了我们悬着的"实体合并后文件怎么办"。
