# 重复消息与幂等入库

## 为什么有这个东西

2026-09-20 早上，一台 Android 手机在约 4 分钟里往 hub 里灌了 **15,745 条**消息，
对应的真实事件只有 **991 个**（同一个 Chrome 通知被存了 271 次）。

链路两端各有一半责任：

* **手机端**：每收到一条通知/短信就触发一次 *全量* 待上传队列同步
  （`ProcessNotificationUseCase` → `syncPendingMemories()`），而且没有任何互斥。
  一次通知风暴里有 56 个通知 → 56 个并发会话各自从队头走一遍，每个条目还会重试
  最多 5 次：`56 × 5 = 280`，实测同一通知出现了 **281** 次。同步又依次被同步
  的顺序（按 key 成簇出现）在数据里留下了指纹。
* **服务端**：`POST /api/v1/messages` 每次都给新 uuid，从来不看这条消息是不是
  已经在了。所以服务端没有任何理由拒绝第 271 份拷贝。

服务端这半边是**可以独立修好的**，也是修在关键路径上的那半边：即使客户端继续
疯狂重试，第 2 次之后的请求也只会得到「已存在」，不会再增加一行。

## 「同一条消息」是怎么判定的

唯一的判定实现在 `message_identity.py`。**入库和清理脚本都调用它**——两套实现
迟早会漂移，而漂移在下次洪水之前是看不见的。

| 情况 | 自然键 |
| --- | --- |
| 推送通知 | `v1\|ntf\|<package_name>\|<notification_id>\|<timestamp>` |
| 有渠道 id 的（短信 / 邮件 / 通话记录） | `v1\|id\|<type>\|<message_id>` |
| 没有渠道 id 的短信类 | `v1\|txt\|<type>\|<sender>\|<timestamp>\|sha1(正文)` |
| 手写的 `NOTE` / `DOCUMENT` | **无**（永不判重） |

要点：

* **手写笔记没有自然键。** 两条文字一模一样的笔记是两件用户想留下的事，不能合并。
* **字段不全就不给键。** 只有 package 没有 notification_id 的推送宁可不去重，也不
  能用一个弱键把不同通知合并掉。
* **`notification_id` 不总是唯一。** 抖音 App 所有通知都用同一个
  `notification_id=2131389425`，真正区分它们的是 timestamp。所以两个字段缺一不可。
* **时间戳只有一种规范化形式。** 入库看到的是 marshmallow 解析出的 datetime，
  清理脚本看到的是 SQLite 读回来的 naive datetime，两者必须落在同一个字符串上，
  否则「重传去重」恰好漏掉清理脚本刚打了键的那些行。见
  `message_identity._stamp()`。
* 键超过 250 字符（列宽 255）时整体做 sha256，**不截断**：两个只有前缀相同
  的不同键不能撞在一起。

## 契约

`POST /api/v1/messages`

* **新消息** → `201`，和以前完全一样。
* **重复上报** → **`200`**，`{"duplicate": true, "id": "<已有消息的 id>", "data": {...}}`。

用 200 而不是 409 是刻意的：重试中的客户端应该把它读成**成功**，这样才会停止重试。
Android 端用 Retrofit 的 `isSuccessful`（2xx 全算成功），浏览器也是。返回已有行的
id 让客户端能把它记下来（附件/提取状态都靠这个 id 去查）。

重复判定发生在**任何附件字节落盘之前**：重传只花一次 SELECT，不会留下一堆没人
引用的 blob。

一个例外：如果这次上报的正文**比已存的那条更长**，就用这次的正文替换已存的正文，
其余字段（包括 metadata）一律不动。这不是假想情况——通知第一次抓到的常常是
「视频标题加载失败」，重试才拿到真标题，只留第一份就把唯一有用的那份丢了。
反向（更短的）不会覆盖更长的。

## 数据库层

`messages.natural_key`（可空）+ 唯一索引 `ix_messages_natural_key`。

* 唯一索引才是真正的保证：应用层的「先查再插」在并发下挡不住两个同时到达的相同
  请求，数据库挡得住。
* 可空 + 唯一在 SQL 里是合法的：NULL 互不相等，所以任意多条无键的行（手写笔记）
  可以共存。
* 索引是在**全 NULL 的列**上创建的（见 `migrate.add_natural_key`），所以可以在
  历史重复还没清理的时候就先加上，之后再回填。

## 清理历史重复

```
./venv/bin/python scripts/dedup-messages.py              # 演练（默认）
./venv/bin/python scripts/dedup-messages.py --report     # 演练 + 逐组明细
./venv/bin/python scripts/dedup-messages.py --apply      # 真删
```

* 默认演练，因为删了就没了。
* 同一组里**留信息量最大的那份**：正文最长 → `received_at` 最早 → id 最小。
* `--report` 会额外列出**同一组里各份拷贝正文不一致**的组，把每个变体都打出来并
  标注哪一份被保留。「最长」是启发式而不是定理（真标题有可能比「加载失败」还短），
  所以这份清单是唯一能看出留错的地方——动手前先读它。
* 脚本同时是 `natural_key` 的**回填器**：键是按行现算的，不看列里已有什么，所以
  键缺失或过期都能修好。

### 故意没有做的：按时间窗合并

清理完还剩 919 条通知，其中 38~56 条是**同一个通知被手机在几毫秒内抓了好几次**
（手机自己给的 `metadata.timestamp` 在几次抓取之间相差 1~40ms，每个不同的时间戳
就是一个不同的键，所以带「视频标题加载失败」的那次不会被并进有真标题的那次）。

看起来用时间窗就能收掉它们，实测**不能**：

| 桶 | 两条相差 | 内容 |
| --- | --- | --- |
| `android` / nid=38 | **1ms** | 两条 Telegram 登录验证码，**账号不同**（1794874969 / 6224730393） |
| `com.yusi.chongchong` / nid=412 | 107~129ms | 两首**不同的歌**（《全世界的雨》/《晴天-周杰伦》） |

也就是说，小到 1~2ms 的窗口就已经会合并真实的不同事件，而 ≥250ms 的窗口会合并
不同歌曲。**所以键保持精确，占位行留在库里**——留下噪声是可以接受的，
把两个不同的手机验证码合成一条不是。

前进方向上的同类情形已经处理好了：如果重试上报的是**同一个时间戳**、只是正文更完整，
入库会替换正文而不是新增一行（见上文）。

## 手机端

服务端这层只是兜底；根因在客户端。`MemorySyncService` 已修两处：

1. 收到一条通知/短信只上传**那一条**（`syncMemory(id)`），不再触发全量扫描；
2. 上传**永不并发**（`Mutex`），全量扫描用 `tryLock` —— 已经在跑就**直接丢弃**而不是排队。

依赖改成函数注入（`di/AppContainer` 是组合根），所以上面这两条并发规则能在 JVM 单测里
跑，而不是只写在注释里。新增的 9 条回归测试做过**反向验证**：把实现退回旧行为后，
其中两条确实失败。
