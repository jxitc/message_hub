# 实体索引（`instance/pkb.db`）

## 一句话

实体索引是**派生数据**：它由 `pkb_extract.py` 从 `instance/message_hub.db` 生成，
随时可以整个删掉重建。**原始消息才是唯一事实来源**，索引里没有任何原始库里没有的东西。

```
instance/message_hub.db        ← 唯一事实来源（消息、附件、OCR 文本）
        │
        │  pkb_extract.py  （LLM 抽实体 + 摘要；日期由代码解析）
        ▼
instance/pkb.db                ← 派生的实体索引（entities / mentions / messages）
        │
        │  pkb_index.py   （只读）
        ▼
/api/v1/entities/*   ·   /entities 网页   ·   问答流水线（qa.py）的召回
```

## 谁产出它

```bash
# 全量重建（默认）。结构变了、或想清掉陈旧行时用。
./venv/bin/python pkb_extract.py

# 增量：只抽索引里还没有的消息。定时任务用这个。
./venv/bin/python pkb_extract.py --incremental

# 试跑
./venv/bin/python pkb_extract.py --limit 40 --db /tmp/x.db
```

成本（实测，1,500 条消息）：**全量 82 秒 / ¥1.27**；**增量在有新消息时 1～2 秒 / ¥0.00**。

## 定时任务

服务器上每小时增量跑一次：

```
systemctl status  message-hub-pkb.timer
systemctl start   message-hub-pkb.service     # 手工触发一次
journalctl -u     message-hub-pkb.service -n 30
```

单元文件里没有重试保护，也**故意**没有：索引是派生数据，跑坏了删掉重建就是，
为它加一套失败重试机制不划算。`Persistent=true` 保证停机期间错过的那次会在开机后补跑。

**做这件事的原因**：索引以前是手工更新的（在笔记本上跑、再把 `pkb.db` 拷到服务器），
而 hub 每天都进新消息——索引会**悄悄过期**，而且没有任何东西会告诉你它过期了。

## 三条不变量

改动抽取器时，这三条不许破。每条都有测试盯着，而且都配了"反向验证"（把代码改回错的样子，
测试必须失败——否则那测试就是同义反复）。

### 1. 实体 id 跨重建稳定

`entities.id` 是**归一化名字的 sha1 前 16 位**，不是自增整数。

真实事故：id 原本是自增整数，而表是每次重建时从零建的、插入顺序取决于**并发批次谁先跑完**。
于是每重建一次，所有 id 全部重排——张丽捷从 71 变成 66，而 71 变成了另一个人。
打开着的页面、书签、问答历史里的 `entities_hit.id` **全都会指错人**。

验证方式：抽取跑两遍、用不同的 `--batch`/`--workers`，共同实体的 id 必须 100% 一致。

### 2. 日期由代码解析，不问模型

`event_date` 来自 `event_dates.py`，模型只输出实体和摘要。

真实事故：退款短信只写了「9月28日」（收到于 9-27），模型把年份猜成了 **2025**。
日期是算术，可以精确、便宜、可审计地做。每条还存下**命中的原串**
（`event_date_raw`）和**年份来源**（`event_date_source`），所以"为什么是这一天"能查。

规则：没写年份的日期取**离收到时间最近的那一次出现**；推不出来就存 NULL，
**不回退成"收到时间"**；一段文本里超过 3 个不同日期就判为无法判定，存 NULL。

### 3. `entities.mentions` 必须等于 `mentions` 表里的行数

真实事故：发信号码传播跑在**统计之后**，被传播补上的提及永远没算进计数——
实测 4 个实体"记 2 实际 4"。计数偏低不会让页面报错，只会安静地少报。

修法不是加测试，而是**让错误顺序写不出来**：两步合成一个 `finalise()`。

## 关于「发信号码传播」

一条短信正文是「线上视频咨询室将于咨询开始前5分钟开启…」，里面没有「简单心理」三个字。
它原先之所以被挂到「简单心理」上，是**因为模型在同一个批次里看到了同号码的续约通知**——
也就是说靠的是批次边界和运气：换个 `--batch` 值、或者重跑一次就可能丢，不可复现。

所以这条改由代码决定：某个发信号码如果有**过半数的消息**（且**至少 2 条**）指向同一个实体，
它发来的、自己没抽出实体的消息就挂到那个实体上，理由写明「同发信号码（该号码 3/4 条消息属于此实体）」。

`min_shared=2` 是为了挡掉「只发过两条、其中一条命中」这种弱证据。
门槛放在"过半"是为了挡掉**转发型发送者**——短信 App（`sender=信息`）把所有来源的短信都转发过来，
没有任何实体能占它一半，于是什么都不传播。这正好是我们要的。

## 从 `info_agent` 搬过来的原因

这套抽取器原先住在 `info_agent/info_agent/pkb/`，和早期的 wiki 编译实验放在一起。
但实体索引已经不再是个实验：它有 REST API、有网页界面、问答流水线依赖它——
**产出 hub 契约的一部分的程序，就该和读它的 `pkb_index.py` 待在同一个仓库里。**

顺带解决了一个具体的麻烦：它以前读的是一个 JSON 导出，而那个导出要在服务器上从
`message_hub.db` dump 出来、拷到笔记本、再把生成的 `pkb.db` 拷回服务器——
索引能有多新，取决于我记不记得手动跑。

> `info_agent` 里那份旧代码**没有删**（那边按要求保持冻结）。两份会漂移，
> 以本仓库这份为准。

## 相关

* `pkb_extract.py` — 产出索引（写侧）
* `pkb_index.py` — 读取索引（读侧，只读连接，索引不存在时页面降级而不是报错）
* `event_dates.py` — 日期解析
* `qa.py` — 问答流水线；它的"日历路由"就是靠 `event_date` 召回未来事件
* `tests/test_pkb_extract_rules.py`、`tests/test_event_dates.py`、`tests/test_entity_links.py`
